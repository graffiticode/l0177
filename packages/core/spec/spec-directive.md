You are given the source of a Learnosity **Author API** integration design (an `author-embed` program — a view function plus a chain of property functions) in this dialect, plus the dialect's canonical knowledge above. Produce a **developer integration RECIPE**: a precise, host-language-NEUTRAL procedure the caller implements in their own stack (Node, PHP, Ruby, .NET, …) to embed the described authoring experience.

Output these sections, in this order, as Markdown:

## Goal
One or two sentences: the authoring experience the developer will have working when done, specialized to the view and the design's specifics (interpolate mode, domain, user, reference, editor options, item bank).

State only what the procedure actually achieves, and be precise about which claims are verified.
A `question-type-groups` restriction IS enforced by the Author API and may be stated as fact ("…and offers only the multiple-choice and cloze groups"). An `allow-widgets` list of question TYPES is not: no confirmed config key restricts at that granularity, so the Goal MUST NOT claim the editor "will restrict" them — phrase those as the design's *intent, pending verification*. Widget edit/delete permissions ARE verified and may likewise be stated as fact.

## Preconditions
What the caller needs before starting: a Learnosity consumer key + secret (secret is **server-only**, never sent to the browser); the official server-side SDK for their language; the serving domain; a stable author user id; the target HTML element. If the design still has unfilled holes (missing required properties), state them here as "you must still provide: …".

## Procedure
Numbered steps. Be SURGICALLY PRECISE where correctness is binary — the `security` object fields and the `YYYYMMDD-HHMM` UTC timestamp, the exact `mode`, that `domain` must equal the serving host, and that the Author API library loads from the BARE host `https://authorapi.learnosity.com` (a versioned path like `/latest/authorapi.js` 404s and yields a blank page) — and ABSTRACT where it's the developer's own choice (their framework, HTTP, templating). Direct the developer to sign with the official Learnosity server-side SDK (do not hand-roll the signature). Cover: build the signed init object server-side; pass it to the page; call `LearnosityAuthor.init(initializationOptions, domSelector, callbacks)`; wire `readyListener`/`errorListener`. Describe only the construct's mode; note there is no in-UI view switching.

**Show the SDK's return value being passed through, not an object you assembled.** The server-side SDK's `init("author", security, secret, request)` RETURNS the complete `{ security, request: { mode, reference?, config, user, organisation_id } }` — request options nested under `request`, not spread at the top level — and that whole return value is what `LearnosityAuthor.init()` takes. Learnosity's docs list `mode`/`reference`/`user` as "initialization options", which reads as a flat object and is the natural wrong guess; assembling one fails at init. Say explicitly that the SDK's output is passed through untouched. Also state the types that bite: `organisation_id` is an **integer**, not a numeric string, and `mode` is the exact string for the view.

**Two init details are binary and were both got wrong in practice — state them exactly.**
- **Argument order.** `init(initializationOptions, domSelector, callbacks)` is the documented order, and Learnosity's demo repo also uses the two-argument `init(initObject, callbacks)` with a defaulted element. NEVER emit `init(initObject, callbacks, "<element>")` — the callbacks land in the selector slot, no listener is registered, and the result is a silent blank editor: the exact failure the recipe's own gotchas warn about.
- **`request.user` is an object, not an id.** Emit `user: { id: "<the design's user-id>" }`, plus `firstname`/`lastname`/`email` when the design carries `user-firstname`/`user-lastname`/`user-email`. A bare `user_id` string fails init with "A user attribute must be provided and be an object when initializing the Author API". A design whose only author information is `user-id` is COMPLETE as a design and still needs this object built at implementation time — say so rather than reporting nothing left to do.

## Gotchas
The specific mistakes that cause silent failures or 401s for THIS experience: domain mismatch, secret leaking to the browser, timestamp skew, missing `errorListener`, (for editing) an omitted `reference`. ALWAYS include these two, which fail silently and are the hardest to diagnose:
- **The Author API fails open on `config`.** An unrecognized `config` key is silently ignored — the editor still initializes, `readyListener` still fires, and the page looks correct while enforcing nothing. A restriction that "looks applied" may not be. Only observing the running editor proves it.
- **A versioned script URL 404s.** `https://authorapi.learnosity.com/latest/authorapi.js` does not exist; `LearnosityAuthor` is then undefined, `init()` never runs, and NEITHER callback fires — a blank page with nothing in the console. Load the bare host.

## Verification steps
A concrete, ordered, runnable acceptance checklist the developer runs against THEIR implementation — each a pass/fail check — so they know they're done. **Output this as a NUMBERED Markdown list — one check per line (`1.`, `2.`, `3.`, …), each a single concrete pass/fail assertion. Do NOT collapse it into a paragraph or a single sentence.** Include at least one negative check. At minimum:
1. `readyListener` fires with no error and the editor renders in the target element. State plainly that this proves INIT ONLY — see the ready-then-error rule below — and never present it as evidence the editor works.
2. The requested item/activity actually loads and its content is visible, with nothing logged to `errorListener` after ready.
3. A deliberately-tampered signature triggers `errorListener` (a 401-class error).
3. The init payload delivered to the browser contains no consumer secret.
4. The `domain` in `security` equals the host serving the page.
Add checks specific to the design (e.g. only the allowed widget types are offered; permissions match; the correct item/activity loads for the given `reference`).

**Any check on config-driven BEHAVIOUR must be differential — including ENABLING keys, not just restricting ones.** Because the Author API fails open, simply observing the desired behaviour proves nothing — the editor may do that by default, with the `config` key ignored. A check like "confirm deletion is unavailable" therefore passes whether or not the config took effect, and is worthless. The same trap applies in reverse to a key that GRANTS a capability (`edit: true`, or any `*: true` permission): the editor very likely permits it by default, so "confirm editing works" passes even if the key was thrown away. Every check on a `config`-driven behaviour — negative or positive, restricting or enabling — must be written as a comparison against a CONTROL init with the key omitted, and state what each outcome means. For example, for `item_edit.widget.delete: false`: "Load the editor twice — once with `config.item_edit.widget.delete: false`, once with that key omitted entirely. If the delete affordance is absent in BOTH, the key changed nothing (the editor hides it by default) and the permission is NOT confirmed to be in force. Only if delete is available in the control and absent with the key set has the config been shown to work." And for the enabling case, `item_edit.widget.edit: true`: "Load the editor twice — once with `edit: true`, once with that key omitted. If widget editing works in BOTH, the key changed nothing (the editor permits editing by default) and the permission is NOT confirmed to be in force." Do NOT let an enabling key off with a bare "confirm editing works" — that is the same worthless check, merely wearing a positive sign. And for a restriction expressed as a LIST that overrides defaults, `question_type_groups`: "Load the editor twice — once with the array as specified, once with that key omitted entirely (control). Confirm the control's picker shows all ten default groups, and the configured run shows only the intended ones. If both runs show the same groups, the key changed nothing and the restriction is NOT in force." A bare "confirm only the intended groups are offered" is the worthless shape again — it passes identically when the config was ignored. Apply this control-comparison shape to EVERY behaviour a `config` key claims to produce, including keys with no worked example above. `organisation_id` takes it too — a control with the org omitted gives the A/B a baseline, and an implementer running it against Learnosity's demo consumer saw the configured org error while the control ran clean, which shows the mechanism works without confirming the org itself. Say what a control-only result does and does not establish: against a demo consumer it demonstrates the mechanism; only the caller's real credentials confirm their own value.

**The error event carries `code` and `message`, not `name`.** `e.name` is `undefined` for both 41003 and 10000 and is only populated when `init()` throws a local `Error`, so a recipe that says "log `e.code`/`e.message`/`e.name`" sends the reader looking for a field that is not there. Direct them to log `code` and `message`, and to label WHICH PHASE the error arrived in — init, or after ready — which is what makes a post-ready 10000 legible instead of looking like a second init failure.

**`readyListener` firing is not a passing check on its own.** It and `errorListener` are not exclusive outcomes: init and content-loading are separate phases, so with an `organisation_id` the consumer cannot access, the editor initializes, ready fires, and only THEN does the content request fail with error 10000. Every recipe must say this where it lists the ready check, and must carry a separate check that the requested content actually appeared. A verification list whose first step is "ready fires" and which treats that as success will pass on an editor that never loaded anything.

Rules:
- **Config paths come from `paths`, never from a key name.** The design ships a `paths` map from each config key it set to its exact Learnosity path. Copy those values verbatim. Do NOT derive a path by expanding a kebab name — the flattening is ambiguous (`title-show` is `title.show`, but `enable-selection` is `enable_selection`), and under fail-open semantics a wrong path yields an editor that looks configured and is not. A key that does not appear in `paths` was rejected by the compiler: leave it out of the recipe entirely rather than guessing where it belongs.
- **Widget/question-type values**: whenever the recipe names question types, use the EXACT lowercase Learnosity strings from the mapping table in the canonical knowledge above (e.g. `mcq`, `clozetext`) — NEVER the UPPERCASE DSL tags and NEVER underscore forms (`MCQ`, `CLOZE_TEXT`, `CLOZE-TEXT` are all wrong).
- **Restriction operates on GROUPS, and that path IS verified.** When the design sets `question_type_groups`, emit `config.dependencies.question_editor_api.init_options.question_type_groups` exactly as the design gives it — the array overrides all ten default groups, omitting `template_references` on those kept and passing `[]` on those removed. Take the path from the design's `paths` map, never by inference. Explain WHY all ten appear: supplying only the wanted groups restricts nothing, because an unrecognised group reference is ADDITIVE — that is precisely the trap that made this key look inert in earlier testing.
- **Question TYPES are a different taxonomy and are NOT restrictable.** `allow_widgets` names question types (`mcq`, `clozetext`); the enforced mechanism selects groups, and one group holds several types. Do NOT invent a per-type config key — because the API fails open, a wrong path is worse than an acknowledged unknown. Name the intended types, state that the restriction is enforced only at group granularity, and carry the per-type expectation as a VERIFICATION STEP. Finer control is possible only via individual `template_references`, whose values are opaque and readable solely from the running editor's picker (`data-lrn-qe-template-reference`) — mention that only if the design asks for per-template control.
- **Never emit these:** `init_options.widgetTypes` (tested, no effect, absent from the current reference) or `config.widget_templates.widget_types` (documented as `{default, show}` — which tile view opens, not a restriction list).
- **Widget edit/delete permissions**: `config.item_edit.widget.edit` / `.delete` (this dialect's `widget` member) are VERIFIED — each independently removes its per-widget affordance, and neither touches the item-level Edit/Preview toggle. State them as fact and emit the paths from `paths`. NEVER use `config.widget_templates.edit`/`.delete` — that path is supported by nothing.
