You are given the source of a Learnosity **Author API** integration design (an `author-embed` program — a view function plus a chain of property functions) in this dialect, plus the dialect's canonical knowledge above. Produce a **developer integration RECIPE**: a precise, host-language-NEUTRAL procedure the caller implements in their own stack (Node, PHP, Ruby, .NET, …) to embed the described authoring experience.

Output these sections, in this order, as Markdown:

## Goal
One or two sentences: the authoring experience the developer will have working when done, specialized to the view and the design's specifics (interpolate mode, domain, user, reference, editor options, item bank).

State only what the procedure actually achieves. If the design restricts widget types, the Goal MUST NOT claim the editor "will restrict" them — that binding is unverified (see the rules below) and asserting it here contradicts the Gotchas and the verification steps. Phrase it as the design's *intent, pending verification* (e.g. "…and is **intended** to offer only `mcq` and `clozetext` — a restriction you must verify in the running editor, as its Learnosity config binding is unconfirmed"). The same applies to widget edit/delete permissions: they are documented-but-unconfirmed, so do not state them as facts the reader can rely on.

## Preconditions
What the caller needs before starting: a Learnosity consumer key + secret (secret is **server-only**, never sent to the browser); the official server-side SDK for their language; the serving domain; a stable author user id; the target HTML element. If the design still has unfilled holes (missing required properties), state them here as "you must still provide: …".

## Procedure
Numbered steps. Be SURGICALLY PRECISE where correctness is binary — the `security` object fields and the `YYYYMMDD-HHMM` UTC timestamp, the exact `mode`, that `domain` must equal the serving host, and that the Author API library loads from the BARE host `https://authorapi.learnosity.com` (a versioned path like `/latest/authorapi.js` 404s and yields a blank page) — and ABSTRACT where it's the developer's own choice (their framework, HTTP, templating). Direct the developer to sign with the official Learnosity server-side SDK (do not hand-roll the signature). Cover: build the signed init object server-side; pass it to the page; call `LearnosityAuthor.init(initObject, callbacks, "<element>")`; wire `readyListener`/`errorListener`. Describe only the construct's mode; note there is no in-UI view switching.

## Gotchas
The specific mistakes that cause silent failures or 401s for THIS experience: domain mismatch, secret leaking to the browser, timestamp skew, missing `errorListener`, (for editing) an omitted `reference`. ALWAYS include these two, which fail silently and are the hardest to diagnose:
- **The Author API fails open on `config`.** An unrecognized `config` key is silently ignored — the editor still initializes, `readyListener` still fires, and the page looks correct while enforcing nothing. A restriction that "looks applied" may not be. Only observing the running editor proves it.
- **A versioned script URL 404s.** `https://authorapi.learnosity.com/latest/authorapi.js` does not exist; `LearnosityAuthor` is then undefined, `init()` never runs, and NEITHER callback fires — a blank page with nothing in the console. Load the bare host.

## Verification steps
A concrete, ordered, runnable acceptance checklist the developer runs against THEIR implementation — each a pass/fail check — so they know they're done. **Output this as a NUMBERED Markdown list — one check per line (`1.`, `2.`, `3.`, …), each a single concrete pass/fail assertion. Do NOT collapse it into a paragraph or a single sentence.** Include at least one negative check. At minimum:
1. `readyListener` fires with no error and the editor renders in the target element.
2. A deliberately-tampered signature triggers `errorListener` (a 401-class error).
3. The init payload delivered to the browser contains no consumer secret.
4. The `domain` in `security` equals the host serving the page.
Add checks specific to the design (e.g. only the allowed widget types are offered; permissions match; the correct item/activity loads for the given `reference`).

**Any check on config-driven BEHAVIOUR must be differential — including ENABLING keys, not just restricting ones.** Because the Author API fails open, simply observing the desired behaviour proves nothing — the editor may do that by default, with the `config` key ignored. A check like "confirm deletion is unavailable" therefore passes whether or not the config took effect, and is worthless. The same trap applies in reverse to a key that GRANTS a capability (`edit: true`, or any `*: true` permission): the editor very likely permits it by default, so "confirm editing works" passes even if the key was thrown away. Every check on a `config`-driven behaviour — negative or positive, restricting or enabling — must be written as a comparison against a CONTROL init with the key omitted, and state what each outcome means. For example, for `item_edit.widget.delete: false`: "Load the editor twice — once with `config.item_edit.widget.delete: false`, once with that key omitted entirely. If the delete affordance is absent in BOTH, the key changed nothing (the editor hides it by default) and the permission is NOT confirmed to be in force. Only if delete is available in the control and absent with the key set has the config been shown to work." And for the enabling case, `item_edit.widget.edit: true`: "Load the editor twice — once with `edit: true`, once with that key omitted. If widget editing works in BOTH, the key changed nothing (the editor permits editing by default) and the permission is NOT confirmed to be in force." Do NOT let an enabling key off with a bare "confirm editing works" — that is the same worthless check, merely wearing a positive sign. Apply this control-comparison shape to widget-type restriction and to EVERY other behaviour a `config` key claims to produce.

Rules:
- **Widget/question-type values**: whenever the recipe names question types, use the EXACT lowercase Learnosity strings from the mapping table in the canonical knowledge above (e.g. `mcq`, `clozetext`) — NEVER the UPPERCASE DSL tags and NEVER underscore forms (`MCQ`, `CLOZE_TEXT`, `CLOZE-TEXT` are all wrong).
- **Widget-type RESTRICTION — never assert a config path.** The `config` binding that restricts which question types an author may add is **UNVERIFIED**: the previously-documented `dependencies.question_editor_api.init_options.widgetTypes` was tested against the live Author API and restricts NOTHING (the picker still offers all ten question-type groups, identical to an unrestricted control). Do NOT emit it, and do NOT substitute another guess — because the API fails open, a wrong path is worse than an acknowledged unknown: it yields an editor that looks restricted but is not. Instead, when the design sets allowed widget types: name the intended types (exact lowercase), state plainly that the Learnosity config binding for this restriction is **not confirmed**, point the developer at Learnosity's Author API initialization reference, and carry the restriction as a VERIFICATION STEP ("open the widget picker and confirm only the intended types are offered — if others appear, the restriction is not in force") rather than as a step that claims to apply it.
- **Widget edit/delete permissions**: Learnosity documents these at `config.item_edit.widget.edit` / `.delete` (matching this dialect's `widget` member). They are NOT functionally verified and the API type-checks neither, so present them as documented-but-unconfirmed and add a verification step. NEVER use `config.widget_templates.edit`/`.delete` — that path is supported by nothing.
